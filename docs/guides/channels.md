# Device-to-Host Channels

NVBit's channel utilities are used by examples that generate more data than is
convenient to report with device `printf` or a small shared counter.

A channel connects a device-side producer (`ChannelDev`) to a host-side
consumer (`ChannelHost`).

## Data flow

```text
instrumented GPU instruction
        |
        v
device instrumentation routine
        |
        v
ChannelDev::push(record)
        |
        v
channel transport / buffers
        |
        v
ChannelHost receiver thread
        |
        v
tool-specific decode, aggregation, or file output
```

The channel moves bytes/records. Your tool defines the record schema and the
meaning of the fields.

## Per-context channel state

A robust tool keeps channel objects in its `CTXstate` because the device
allocation and CUDA context are related.

Typical state includes:

- `ChannelDev*` or the storage backing it;
- `ChannelHost`;
- receiver-thread state;
- flags used to terminate/drain the receiver;
- optional helper-module/function state for flushing.

## Initialize in `nvbit_tool_init`

Channel setup commonly needs CUDA-managed/device memory. Do not perform that
allocation in `nvbit_at_ctx_init`; NVBit warns that CUDA allocations from the
context-init callback can deadlock.

In `nvbit_tool_init`:

1. allocate the device-visible channel state;
2. initialize `ChannelHost` with the corresponding device channel;
3. start/obtain the receiver thread;
4. call `nvbit_set_tool_pthread(receiver_thread)`.

## Why register the receiver thread?

The receiver is part of the tool, not the target application. If it performs
CUDA work, its driver calls should not recursively trigger the tool's normal
application callbacks.

`nvbit_set_tool_pthread()` tells NVBit to suppress callbacks generated by the
registered tool thread. Matching cleanup should unset/terminate thread state as
appropriate for the tool.

## Record design

Channel throughput depends heavily on record size.

Prefer:

```cpp
struct Record {
    uint32_t instruction_id;
    uint32_t flags;
    uint64_t launch_id;
    uint64_t address;
    // compact dynamic fields
};
```

over repeated text fields such as full function and opcode names. Maintain
static dictionaries on the host.

Make the schema version explicit if traces will be persisted.

## Backpressure and receiver work

A producer can outpace a receiver. Keep the receiver's hot path short:

- copy/decode records;
- append to a buffered output;
- aggregate simple counters.

Expensive formatting, JSON serialization, compression, or analysis can be
delegated to another stage if necessary.

## Flushing

A channel must be drained before its backing memory is destroyed.

Modern NVBit provides explicit tool-module APIs that allow a tool to embed and
launch a helper kernel used for flushing. This is preferable to depending on
lazy loading of a tool kernel during a callback path.

The high-level termination sequence is:

```text
prevent new target work
      |
wait for required GPU completion
      |
launch/trigger channel flush
      |
receiver consumes final records
      |
stop and join receiver
      |
free channel state
```

The exact handshake is implemented by the channel utility/example and should
be preserved when adapting it.

## Synchronization is part of correctness

A device-to-host trace is not correct merely because most records arrive.
You must know when:

- the producer finished writing;
- the host can observe those writes;
- the final notification has been consumed;
- it is safe to free the channel.

Do not replace the example's ordering/fence logic with an unchecked "sleep and
hope" mechanism.

## Avoid unnecessary kernel serialization

Older tracing approaches often synchronized after every kernel because it made
output ordering simple. That can distort applications with stream concurrency.

The modern 1.8 lineage of `mem_trace` avoids unconditional default
serialization. Preserve asynchronous behavior unless your output contract
specifically requires per-launch blocking.

## When not to use a channel

A channel may be unnecessary for:

- one scalar counter;
- a small histogram in managed/device memory;
- a debugging message emitted rarely;
- state that can be copied after a known synchronization point.

Use the simplest communication mechanism that meets the data-volume and
ordering requirements.
